一、通用的配置文件格式

1. JSON

起源：由 Douglas Crockford 在 2001 年推广，源自 JavaScript 的对象表示方式。

发展：成为 Web API 通信和配置的通用格式，广泛用于 Node.js、VSCode 等工具。

特点：

  • 支持嵌套、数组、对象
  • 严格语法（必须双引号）

优点：

  • 通用性强
  • 易于解析和序列化

缺点：

  • 不支持注释
  • 可读性略低于 YAML

使用场景：

  • package.json：Node 项目依赖配置
  • tsconfig.json：TypeScript 编译配置
  • .eslintrc.json、.prettierrc：代码风格工具配置

2. YAML

起源：2001 年，Clark Evans、Ingy döt Net 和 Oren Ben-Kiki 创建

发展：逐渐取代 XML，用于 DevOps、K8s、配置管理工具（如 Ansible）

特点：

  • 缩进结构
  • 支持注释（#）

优点：

  • 可读性好
  • 支持复杂嵌套

缺点：

  • 缩进敏感，容易出错
  • 不适合机器生成

使用场景：

  • application.yml：Spring Boot 配置
  • docker-compose.yml：容器编排
  • GitHub Actions 工作流配置

3. JS/TS

起源：Node.js 模块系统（CommonJS/ESM）支持配置以 JS 编写

发展：随着构建工具、框架的可编程化发展（如 Webpack/Vite），JS 配置成为主流

特点：

  • 完全可编程（可用变量、函数、条件）

优点：

  • 动态生成配置（适合多项目、条件判断）
  • 灵活组合

缺点：

  • 解析成本高
  • 不易被静态工具读取

使用场景：

  • webpack.config.js / vite.config.ts：构建工具配置
  • tailwind.config.js：样式引擎配置
  • babel.config.js：转译配置

4. INI/.env

  • 起源：INI 最早用于 Windows 系统设置文件（如 win.ini）；.env 则起源于 Twelve-Factor App 方法（Heroku 推广）。
  • 发展：.env 格式逐渐成为跨语言的环境变量标准，配合 dotenv 等库使用。
  • 特点：
    • 简洁的键值对：KEY=VALUE
    • 不支持嵌套或复杂结构
  • 优点：
    • 极其轻量
    • 跨语言支持好
  • 缺点：
    • 类型不明（都是字符串）
    • 无结构，不适合复杂配置
  • 使用场景：
    • 前后端项目的环境变量配置（如 API_URL、DB_PASS）
    • CI/CD 环境变量注入

5. TOML

起源：由 GitHub 联合创始人 Tom Preston-Werner 创建（2013）

发展：Rust 社区率先采用（如 Cargo），后被 Python、Hugo 等工具接纳

特点：

  • 支持注释、结构清晰
  • 类似 INI 但支持类型系统

优点：

  • 类型明确（支持字符串、日期、数组等）
  • 易读性和可维护性较好

缺点：

  • 生态不如 YAML/JSON 完善

使用场景：

  • pyproject.toml：Python 打包与工具配置
  • Cargo.toml：Rust 项目管理
  • Hugo 博客配置

6. XML

起源：W3C 标准，用于结构化数据交换

发展：早期配置与数据传输首选，现在逐渐退居二线

特点：

  • 标签结构清晰，可定义 schema

优点：

  • 可验证性（XSD）
  • 可扩展性

缺点：

  • 冗长，可读性差

使用场景：

  • pom.xml：Maven 项目依赖管理
  • 早期 Java EE 应用配置

7. Properties 文件（.properties）

起源：Java 社区传统配置格式

发展：早期广泛用于 Java Web 项目，后逐渐被 YAML 取代

特点：

  • 键值对结构，支持注释

优点：

  • 简单易用

缺点：

  • 不支持复杂嵌套
  • 不适合结构性配置

使用场景：

  • application.properties：Spring Boot 配置（兼容）
