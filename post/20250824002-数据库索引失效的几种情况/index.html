一、索引失效的核心原理

  • 索引本质是 B+ 树（或其他数据结构），查找时要求：
    • 索引列直接参与条件
    • 条件支持范围查找或等值查找
  • 索引失效就是 MySQL 优化器决定 不走索引，全表扫描。

二、常见导致索引失效的情况

1️⃣ 对索引列进行函数/表达式运算 

SELECT * FROM user WHERE DATE(create_time) = '2025-08-24';
SELECT * FROM user WHERE id + 1 = 101;
  • 原因：B+ 树索引存的是列原始值，函数/运算会改变原值 → 无法用树查找
  • 优化：用范围条件替代函数
WHERE create_time >= '2025-08-24 00:00:00' 
  AND create_time < '2025-08-25 00:00:00'

2️⃣ 前置通配符 LIKE 

SELECT * FROM user WHERE name LIKE '%Alice';
  • 原因：B+ 树索引按字典序存储，前置通配符破坏顺序
  • 优化：
    • 改为前缀匹配：LIKE 'Alice%'
    • 或使用全文索引/倒排索引

3️⃣ 数据类型不匹配或隐式转换 

SELECT * FROM user WHERE id = '101';
  • 若 id 是 int → MySQL 会把 id 转成字符串或把 ‘101’ 转成 int
  • 索引可能失效
  • 优化：保证类型一致

4️⃣ OR 条件跨列 

SELECT * FROM user WHERE age=20 OR name='Alice';

  • 原因：MySQL 对 OR 的优化有限，如果条件跨列且没有覆盖索引，可能走全表

  • 优化：

    • 使用 UNION 拆分查询
    SELECT * FROM user WHERE age=20
UNION
SELECT * FROM user WHERE name='Alice';
    • 或创建联合索引覆盖 OR 条件（有限支持）

5️⃣ 索引列前有运算或类型转换

  • 示例：
SELECT * FROM user WHERE YEAR(birthday) = 2025;

  • 优化：

    • 使用范围条件替代函数
    WHERE birthday >= '2025-01-01' AND birthday < '2026-01-01'

6️⃣ 索引列参与 IS NULL / NOT IN / <> 等操作 

SELECT * FROM user WHERE name IS NULL;
SELECT * FROM user WHERE name <> 'Alice';
SELECT * FROM user WHERE id NOT IN (1,2,3);
  • B+ 树索引不适合做负向查询
  • 优化：
    • 改写逻辑为正向条件
    • 尽量避免 NOT IN、<>、IS NULL 高频查询

7️⃣ 联合索引没有遵循最左前缀原则 

CREATE INDEX idx_user_age_name ON user(age, name);

SELECT * FROM user WHERE name='Alice'; -- 不走索引
  • 原因：B+ 树联合索引要求查询条件包含最左列
  • 优化：
    • 调整索引列顺序
    • 单独建索引

8️⃣ 数据量太小 / MySQL 优化器认为全表扫描更快

  • 小表或者索引选择性低时，优化器会自动选择全表扫描
  • 这不是真正意义上的“索引失效”，是优化器成本估算结果

9️⃣ 复合索引使用不当

  • 示例：
CREATE INDEX idx_user_age_name ON user(age, name);

WHERE age=20 AND name LIKE '%Alice'; -- 索引只对 age 有效
  • 前置通配符、函数、类型不匹配等都会导致复合索引部分失效

三、总结

情况 原因 优化方法
索引列函数/表达式 改变原值 用范围或等值替代函数
前置通配符 LIKE B+ 树顺序破坏 前缀匹配 / 全文索引
类型不匹配 隐式转换失效 保持类型一致
OR 条件跨列 索引无法覆盖 拆查询 / UNION / 联合索引
NOT IN / <> / IS NULL B+ 树不适用 改写正向查询
联合索引最左列缺失 最左前缀原则 调整索引顺序或建单列索引
数据量小 / 优化器判断 全表更快 无需优化
索引列更新频繁 / 前置运算 B+ 树定位困难 避免运算 / 临时索引
